# Architecture: module contracts

## Step 74d: reusable carry, floes, warmth and guides

All four mechanics are session-only and host-authoritative. Their only current consumer is `world/mechlab.js`, constructed once by `main.js` when `?mechlab` is present. Without the flag there are no new courses, colliders, targets, creatures or slippery surfaces. `game/save.js` disables central game-state reads, writes and clears for the entire mechlab session; no storage key is added. Use `?mechlab` on both screens for network testing. The wolf is a WIP model, not a registered pet; no 74e quest state exists.

- **Carrying:** `game/carryLogic.js` exports `createCarryState(defs)`, `carriedBy(state,key)`, `validatePick(state,key,id,pos)`, immutable `applyPick` / `applyDrop`, `putDown(pos,yaw,safe)` and `waterDrop(checkpoint)`. `safe(x,z,fromY)` returns a finite floor height or null; put-down tries six directions, beginning in front, and refuses water/colliders. `game/carry.js` exports `createCarry({sync,defs,safe,actors,checkpoint})`: `pick(player,id)`, `drop(player)`, `fall(player)`, `update()`, `carried(key)`, `state`, `summary()`. `actors()` supplies active `{key,pos,yaw}` entries; `checkpoint(key)` supplies a host-owned safe point, never a client-specified drop destination. Domain **`carry`** snapshots/events are `{objects:{id:{carryable,x,y,z,carrier:null|actorKey}}}`. Requests `pick {id}`, `drop {}`, `fall {}` validate ownership/reach and serialize races; local departure / `screenLeft` releases the object. No replica prediction. The screen adapter sets `player.carrying`, attaches its model to the rig's chest, hides held tools and pets, and chains splash/catch hooks. `player.js` multiplies speed by `CARRY.speed=.75`, hop launch by `CARRY.jump=.85`, blocks tool swings and raises both arms. Existing tool ownership is preserved and visibility restored on release/departure. Debug methods take the actual Player object, including any local slot, not a hard-coded P1.
- **Floes:** `game/hopLogic.js` adds `kind:'floe'`, closed-ellipse `{kind:'drift',amp,depth?,period,phase?}`, `{kind:'spin',period,phase?}` and `{kind:'tilt',period}`. `padPos(pad,hostSeconds)` returns the existing fields plus `rot,pitch,roll`; it is deterministic given the pad's replicated `load:{x,z,sink}`. `padTop(pad,pose,x,z)` answers the loaded plane. `game/iceLogic.js` exports exponential `slideVelocity(v,target,dt,grip)`, `rideFloe(point,before,after)` and `tiltLoad(occupants,pad)`. `game/ice.js` exports `createIce({sync,pads,actors,clock})`, `update()` and `summary()`; domain **`ice`** snapshots/events are `{padId:{x,z,sink}}`, quantized to .01, counted only by the host from grounded player poses. Replicas only apply loads. Two players increase sink. Player bodies ride translation and rotation; footing uses `ICE.grip=3.2` only on floes or explicitly authored `slippery` pads. Ground type `ice` is untouched. Moving floes bypass the landing magnet. The course validator samples the motion cycle and searches real flight windows for `wait` links; drift waits may exceed the static worst-gap limit only if actual timed flights succeed. `validateCourse(course,T,{jumpScale,speedScale})` also verifies reduced carry travel; floe landings include momentum braking and pad riding. `world/hopCourses.js` uses one instanced mover mesh per pad kind, merged still pads, shared toon ice opacity .9, and the existing glint/catch effects; summary includes each floe's motion, pose and load. Register once, independently of visual rebuilds.
- **Warming:** `game/warmLogic.js` exports `warmth(value,dt,{pos,fire,fuel,carried},gift=0) -> 0..1`. Only positive real fuel, an object put down within `WARM.radius=2.2`, and compatible floor height allow progress/gifts. Rate is `1/30` per second; a debug gift adds `.25`; no decay or time-of-day input. `game/warm.js` exports `createWarm({sync,ids,context})`, `update(dt)`, `give(id,n=1)`, `state`, `summary()`. Domain **`warm`** snapshots/events are `{objectId:warmth}`; only host updates advance time, and the current `gift {id,n}` request is a host-only debug grant, not an inventory-spending API. Future quest consumers must validate/spend their own gifts before granting warmth. Presentation blends frost colour/emissive without a light, reduces shivering, and uses pooled particle steam.
- **Guide:** `game/guideLogic.js` exports `freshGuide(path)`, `startGuide(path,players)` and immutable `stepGuide(state,path,players,dt)`; waypoints are `{x,y,z,hop?,balance?,slide?}` (balance/slide surface authoring belongs to the consuming course). It enrolls active players within `GUIDE.range=18` at start, runs at `3.2 u/s`, waits if the slowest enrolled active player is more than `6 u` away, resumes on return, and catches falls or losses beyond `24 u` to each player's last reached waypoint. Players on unrelated islands do not enroll. `hop` produces an .8 u arc. `game/guide.js` exports `createGuide({sync,paths,players})`, `start(id,player)`, host-debug `reset(id)`, `update(dt)`, `state`, `summary()`. Domain **`guide`** snapshots/events are `{guideId:{running,index,x,y,z,waiting,checkpoints:{actorKey:index},catches:{actorKey:{x,y,z,serial}}}}`; start requests are range-checked, replicas never step, host emits progress/catches. Each owning screen applies catch serials once as teleport+puff. The adapter supplies playable hop/log surfaces, animates the WIP wolf's trot/wag and a low existing squawk as a bark cue, and never unlocks a pet.

`world/islands/mechlabPlan.js` is deterministic, pure layout on real terrain: carry `(-5,-152)`, fire `(-5,-169)` / warm approach `(-5,-167.2)`, floes start `(-25,-91,.25)` and end `(-14.5,-86.1,.25)`, guide ten waypoints from `(-26,-151)` to `(-26,-124)` with one hop and a 1.4 u wide slippery log over a catch zone. Guide pads and the floes pass the existing flight validator; both directions of the floes also pass with carry travel. Placement checks include seeded prop colliders, camp stage footprints and critter dens. The debug adapter registers two targets and zero collider-registry entries; its two courses supply their own surfaces/hazard.

Budget (structural Node counts, not GPU measurements): snowball 1 draw, merged route/gully markers 1, WIP wolf 1 main + 1 sun-shadow = **4**; floes 1 mover instance mesh + merged still mesh/outline = **3** before glints; guide platforms merged mesh/outline = **2**. At most four shared glint rings: **13** additional submissions in the four-player worst case, **10** with one ring. No new lights. Runtime shows these only with Frostpine full detail; course hide/rebuild never duplicates targets. Browser visuals, real renderer counts, audio/feel and real two-screen/device play remain unverified here.

## Step 75: campfire tool racks

`game/toolRackLogic.js` exports `rackKinds(discovered)`, `rackUnlocked(quests, fire)`, `decideCycle(heldInfo, stock, kinds)`, `rackId(base, fire, slot, kind)`, `rackInfo(base, id)` and `RACK_COUNT`. The pure cycle returns `{put, drop, take, line}`: only an owner's copy at its original rack is returned, other held items are tossed aside and away from the rack, out copies are skipped, and a lone held copy is kept. There is no empty cycle step.

`world/toolRackPlan.js` exports `toolRackPlan(options)`, a deterministic read-only fan search from +Z after static world registrations. It samples dry walkable terrain across the footprint, checks rise/slope, paths, colliders and static interactables, and reserves future furniture, garden plots, Mossback and the pet stable. Main passes the already chosen Carle collider as `reserved`, including before Carle unlocks. Moving critters / Tdoongz and ground item interactables do not steer static placement. `items/spawns.js` owns the unchanged fixed DEFS seeds; rack placement keeps at least 2.5 u from them and from all registered static interactable centres, after gathering registers its bushes, herbs and dig spots. `finalRackObstacles()` reads every Frost camp / Ember garden stage, including collider-free roof spans, channels, stepping stones, beds and decor; locked cosmetic stands, garden plots, marsh seats/rods and the whole pet stable reservation are also excluded. The whole close fan is tried before successively larger fallback rings. **Placement exception:** FIRES frost.clear=14 and ember.clear=10 conflict with the required 4.5?6.5 distance. `TOOL_RACK.nearClear=5` limits those camp-area reservations for this intentional camp furniture; the home and dusk rings are respected. Their FIRES data is unchanged. The final Ember layout requires the 8.5 u fallback ring; safety and final-stage clearance take priority over the original 6.5 u maximum.

`world/toolRacks.js` exports `createToolRacks(...)`. Unlock derives from `quests.slots[fire].last`, waits for a replica's first synced snapshot, pops live with `world/popIn.js`, and loads silently. It registers one collider and one `toolrack` interactable once per rack, independently of island visibility/rebuilds. It uses the world's full-detail flag, one merged outlined stand and one merged outlined peg display. Display stock is the union of local non-bot slots; unavailable pegs dim. Rod is gated by `boat.state.discovered`. The shared toon materials add no shader or light. `update(dt)`, `prompt(player,fire)`, `plan` and the README debug API form its public API.

The **items domain** remains the authority for all copies. `configureRacks(access)` supplies gates, reach positions, allowed actors, kinds and local labels; `cycleRack(player,fire)`, `rackStock(slot,fire)`, `rackDecision(player,fire)` and host-only `resetRacks()` expose rack operations. Host validates fire unlock, range (INTERACT_RADIUS + rack radius + remote slack), slot ownership, cinematic/global/local freezes, leaving/away and pickup cooldown. Request: `rack {fire}`. Event: `rack {actor:{screen,index}, fire, put:id|null, drop:{id,spot,yaw}|null, take:id|null, from:{x,y,z}, line:string|null}`. One event atomically returns/drops/takes on every screen. Extra `from` supports remote toss/return flights; `line` carries exhausted-stock feedback. Debug host reset broadcasts `rackReset {}`. No replica predicts stock. Rack drops use the existing item toss and findSpot search, preferring 1.6-2 u sideways/outward, walkable ground beyond the rack reach, and a wider safe search when blocked. `interactables.findNearest` gives only a reachable `toolrack` in its narrow +Z front approach priority; other types, side/back approaches, filters, range and registration-order ties retain their distance rules.

Copies carry `rack:{fire,owner,kind}`. The reserved layout is `base + fireIndex*20 + slot*5 + kindIndex` (FIRES order home/frost/ember/dusk; kinds axe/hammer/sword/shovel/rod). Production fixed records occupy 0?94, rack reservations 95?174, dynamic special/ethereal records start at 175 (Step 86b: now 179, see "Homesteading unlock" below: the 80 ids above never shifted). Lightweight records exist immediately; item models/ground resources are built only on first take or late snapshot of a used copy. Canonical place is `rack`, `held` or `out`; animation states `toHand`, `remote`, `tossing`, `landing`, `ground` and cosmetic `toRack` map onto those places. A rack copy in stock has no world mesh presentation, interactable or collider. Snapshot entries include `rack` and `place`; `hashView` includes canonical place/holder/ground spot, excluding presentation timers. The return flight changes stock immediately.

No storage key is added. Rack state is never saved by the host; `rememberedTool` rejects any record with `rack`, so a host reload recreates all reservations in stock and held copies disappear. A replica reconnect instead adopts the current host session snapshot. Existing drops/swaps/screen-grace expiry send copies out. Anyone can pick them up, but only the original slot can return one to its original rack. Reusing a departed slot inherits its remaining stock for that session.
